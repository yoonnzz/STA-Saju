# 004: 사주 해석 결과 데이터베이스 저장

## 목적

Google로 로그인한 사용자의 가장 최근 정상 사주 해석 결과 1개를 Supabase 데이터베이스에 저장한다. 사용자는 같은 계정으로 다시 로그인했을 때 다른 브라우저나 기기에서도 최근 결과를 불러볼 수 있다.

## 결정된 내용

- 데이터베이스는 Google 로그인과 같은 **Supabase 프로젝트**를 사용한다.
- 사용자마다 **가장 최근 정상 결과 1개만** 저장한다. 새 결과가 저장되면 이전 결과를 교체한다.
- 로그인하지 않은 사용자는 기존처럼 브라우저의 `localStorage`에 최근 결과 1개를 저장한다.
- 로그인한 사용자가 새 Gemini 해석을 정상적으로 받으면 데이터베이스에 자동 저장한다. 저장 중임과 저장 완료 여부를 화면에 알린다.
- 로그인 전에 브라우저에 있던 결과는 로그인 직후 자동으로 서버에 올리지 않는다. 사용자가 `이 결과를 내 계정에 저장`을 눌렀을 때만 저장한다.
- Gemini 호출이 실패했거나 응답 형식 검사를 통과하지 못한 결과는 데이터베이스에 저장하지 않는다.
- 원본 생년월일과 출생시간은 데이터베이스에 저장하지 않는다. 화면을 다시 만드는 데 필요한 계산 결과와 해석 결과만 저장한다.

## 사용자 흐름

### 로그인 상태에서 새 해석을 만든 경우

1. 사용자가 생년월일과 출생시간을 입력하고 Gemini 해석을 요청한다.
2. 서버가 기존 Spec 002의 방식으로 입력을 검증하고 사주를 계산한 뒤 Gemini 해석을 확인한다.
3. 정상 결과가 화면에 나타나면 `계정에 저장하고 있습니다…`라고 표시한다.
4. 데이터베이스 저장이 끝나면 `내 계정에 저장되었습니다.`라고 표시한다.
5. 같은 사용자가 새 정상 해석을 만들면 이전 저장 결과를 새 결과로 교체한다.

### 다시 방문한 경우

1. Google 로그인이 확인되면 데이터베이스에서 해당 사용자의 최근 결과 1개를 가져온다.
2. 저장 결과의 형식과 버전을 확인한 뒤 화면에 표시한다.
3. 저장 결과가 없으면 빈 화면으로 두지 않고 `아직 저장된 해석이 없습니다.`라고 안내한다.
4. 데이터베이스 결과를 가져오지 못하면 기존 브라우저 저장 결과가 있을 때 이를 유지하고 다시 시도할 수 있게 한다.

### 로그인 전에 만든 결과가 있는 경우

1. 로그인 전에 만든 정상 결과는 브라우저에 그대로 둔다.
2. 로그인 후 `이 결과를 내 계정에 저장` 버튼을 보여준다.
3. 사용자가 버튼을 누른 뒤에만 현재 계정의 최근 결과로 저장한다.
4. 계정에 이미 저장된 결과가 있다면 교체된다는 점을 버튼을 누르기 전에 알린다.

## 데이터 구조

테이블 이름은 `saju_readings`로 한다. 한 사용자에게 한 행만 허용한다.

| 항목 | 데이터 형태 | 용도 |
|---|---|---|
| `id` | UUID | 저장 행을 구분하는 번호 |
| `user_id` | UUID | Supabase 로그인 사용자와 연결하는 값 |
| `chart` | JSON | 네 기둥, 일간, 오행 분포 등 검증된 계산 결과 |
| `reading` | JSON | 핵심 요약, 성향, 일·진로, 관계, 예시와 근거 |
| `schema_version` | 정수 | 저장 형식의 버전. 처음 값은 `1` |
| `reading_created_at` | 날짜·시간 | Gemini 해석이 정상적으로 만들어진 시각 |
| `created_at` | 날짜·시간 | 데이터베이스 행이 처음 만들어진 시각 |
| `updated_at` | 날짜·시간 | 최근 결과로 교체된 시각 |

- `user_id`는 `auth.users.id`와 연결하고 중복을 허용하지 않는다. 이 규칙으로 사용자마다 최근 결과 1개만 유지한다.
- `id`, `created_at`, `updated_at`은 데이터베이스가 만든다. 브라우저가 임의로 정한 값을 그대로 믿지 않는다.
- `chart`와 `reading`은 저장 전과 불러온 뒤 모두 앱의 현재 형식 검사 함수를 통과해야 한다.
- 이메일, Google 프로필, API 키, 인증 토큰, 서버 오류 원문, 사용자의 질문은 이 테이블에 저장하지 않는다.

## 저장 규칙

- 로그인 사용자의 ID는 요청 내용에서 받지 않고, Supabase가 확인한 서버 세션에서 가져온다.
- 같은 사용자의 행이 없으면 새로 만들고, 있으면 `chart`, `reading`, `schema_version`, `reading_created_at`, `updated_at`만 바꾼다.
- 저장 요청에는 클라이언트가 계산했다고 주장하는 임의의 결과를 그대로 받지 않는다. 정상 Gemini 해석을 만든 서버 흐름에서 검증된 결과를 저장한다.
- 로그인 전에 만든 로컬 결과를 계정에 옮길 때도 현재 데이터 형식 검사를 다시 수행한다.
- 사용자가 저장 버튼을 여러 번 누르거나 같은 요청이 반복되어도 한 행만 남는다.
- 저장 성공을 확인하기 전에는 화면에 `저장됨`이라고 표시하지 않는다.

## 불러오기와 우선순위

- 로그인 상태에서는 데이터베이스의 최근 정상 결과를 계정 결과로 사용한다.
- 데이터베이스에 결과가 없고 브라우저에 로컬 결과가 있으면 자동 업로드하지 않고 저장 버튼을 제공한다.
- 데이터베이스 결과가 깨졌거나 지원하지 않는 버전이면 화면에 표시하지 않는다. 기존 로컬 결과까지 자동으로 지우지 않는다.
- 다른 사용자로 로그인하면 이전 사용자의 화면 결과와 계정 캐시를 즉시 치우고 새 사용자의 결과만 조회한다.
- 로그아웃하면 계정에서 불러온 결과를 화면에서 제거한다. 브라우저에 원래 있던 익명 사용자의 로컬 결과를 삭제할지는 구현 시 별도 공간으로 구분해 섞이지 않게 한다.

## 개인정보와 보안

- 테이블에 **행 수준 보안(RLS)**을 켠다. 이는 데이터베이스가 “현재 로그인한 사람의 행만 허용”하도록 검사하는 장치다.
- 조회, 생성, 수정, 삭제 정책 모두 `auth.uid() = user_id`인 경우만 허용한다.
- 브라우저에서는 공개 가능한 Supabase publishable key만 사용한다. 서비스 전체 데이터를 읽을 수 있는 service role key를 브라우저 코드에 넣지 않는다.
- 서버에서도 로그인 세션을 확인하며, 전달받은 `user_id`만으로 본인이라고 판단하지 않는다.
- 데이터베이스 오류 원문, 내부 테이블 구조, 인증 정보는 사용자 화면에 표시하지 않는다.
- 결과 삭제 기능을 구현할 때도 본인의 행 하나만 삭제할 수 있게 같은 보안 정책을 사용한다.

## 실패와 재시도

- 해석 생성은 성공했지만 저장만 실패하면 해석 결과는 화면과 `localStorage`에 유지한다. `해석은 만들었지만 계정에 저장하지 못했습니다.`라고 알리고 저장 재시도 버튼을 제공한다.
- 불러오기가 실패하면 저장된 결과가 없다고 단정하지 않고 `저장된 결과를 불러오지 못했습니다.`라고 구분해 안내한다.
- 로그인 세션이 만료됐으면 저장하지 않고 다시 로그인하도록 안내한다.
- 중복 요청, 느린 네트워크, 브라우저 새로고침이 발생해도 동일 사용자에게 여러 행이 생기지 않아야 한다.
- 지원하지 않는 저장 버전이나 잘못된 JSON은 결과로 표시하거나 다시 저장하지 않는다.

## 확인 기준

1. 로그인 사용자가 정상 Gemini 해석을 만들면 `saju_readings`에 그 사용자의 행 1개가 생긴다.
2. 같은 사용자가 새 해석을 만들면 행이 늘어나지 않고 최근 결과로 교체된다.
3. 새로고침하거나 다른 브라우저에서 같은 Google 계정으로 로그인하면 최근 결과를 다시 볼 수 있다.
4. 로그인하지 않은 사용자의 결과는 데이터베이스에 저장되지 않고 기존 `localStorage` 방식으로만 유지된다.
5. 로그인 전에 만든 로컬 결과는 사용자 버튼 입력 없이 자동으로 데이터베이스에 올라가지 않는다.
6. 사용자 A는 사용자 B의 결과를 조회·수정·삭제할 수 없다. 데이터베이스 정책 테스트로 확인한다.
7. 잘못된 해석, 지원하지 않는 버전, 저장 실패에는 가짜 성공 표시가 나오지 않는다.
8. 원본 생년월일, 출생시간, API 키, 인증 토큰이 데이터베이스 행과 브라우저용 코드에 포함되지 않는다.
9. 타입 검사, 자동 테스트, 빌드, 실제 로컬 화면에서 저장·교체·복원·실패 흐름을 확인한다.

## 이번 Spec에서 제외

- 여러 사주 결과를 목록으로 보관하는 기능과 즐겨찾기.
- 결과 이름 붙이기, 수정 기록, 휴지통, 장기 보관 기간 설정.
- 다른 사용자에게 공개하는 공유 링크.
- 계정 삭제와 모든 데이터 일괄 삭제. 계정 기능 확장 시 별도 Spec으로 정의한다.
- Gemini 해석 내용과 카테고리 자체의 변경. 이 Spec은 정상 결과의 저장과 복원만 다룬다.

## 구현 순서

1. `saju_readings` 테이블, 사용자당 한 행 제약, 행 수준 보안 정책을 마이그레이션으로 만든다.
2. 로그인 세션을 기준으로 저장·불러오기 기능을 만든다.
3. 기존 `localStorage` 결과와 계정 결과가 섞이지 않도록 화면 상태를 연결한다.
4. 저장 중·성공·실패·재시도 문구를 화면에 추가한다.
5. 두 사용자 분리, 최신 결과 교체, 로그인 전 결과의 수동 저장을 자동 테스트와 실제 화면에서 확인한다.
